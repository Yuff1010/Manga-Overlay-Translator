# 优化与迭代方向(Optimization Roadmap)

> 本文档基于对当前代码库的完整审读整理而成,列出后续优化与迭代的候选方向。
> 定位是**方向清单与决策参考**,不是承诺的开发计划;每个方向都标注了对应的
> 代码位置、预期收益和风险,落地前应单独评估。
>
> 文中的代码引用以撰写时(userscript v0.13.0、git `5b2d3b9`)为准,行号可能随
> 后续提交漂移,以文件/函数名为准。

## 1. 高性价比方向(现状已有明确缺口)

### 1.1 补齐自动化测试

**现状**:`server/tests/test_smoke.py` 只覆盖纯函数(profile 加载、fence 剥离、
`_unpack`、脚本打分、垃圾过滤、行合并、实例池回滚、气泡冷却)。API 层和真实
OCR 链路没有自动化保障。

**PRD 第 16 节已立项的欠账**:

- `GET /ping`、`GET /config` 响应形状与"不返回密钥"约束;
- `POST /translate` 坏图片 → 400、非法 profile → 400、缺 API Key 时返回
  原文且 `translated=false`;
- 用程序生成的已知文字图片做 OCR fixture 测试(断言坐标与文本);
- 本地 HTML fixture 供 userscript 手动回归(候选收集、覆盖层定位)。

**建议**:先补 API 层测试(用 FastAPI TestClient + 桩掉 OCR/翻译),再补 OCR
fixture(需要 PaddleOCR 环境,标记为慢测试)。这是最便宜的信任积累,任何后续
方向动代码前都应有它兜底。

### 1.2 术语一致性:角色名/专有名词跨页记忆

**现状**:`server/translator.py` 的 `translate_texts()` 是无状态的——每次
`POST /translate` 独立成批,LLM 看不到之前页面。同一部漫画里的角色名、招式名
、地名可能每页被翻成不同译法,阅读体验割裂。

**方向**:

- 后端维护极小的术语缓存(如 `术语 → 固定译名`,带 TTL/容量上限),把
  "本域名或本轮出现过的专有名词"注入 SYSTEM_PROMPT;
- 或由用户脚本把已翻页面里的高频词随请求上传(用户脚本无密钥,术语表放在
  浏览器侧或服务端均可,不违反安全约束);
- 附带解决 PRD 第 17 节遗留问题:是否展示估算成本——可加 `cost` 字段,按各
  供应商价格表估算,面板直接显示金额而非只有 token 数。

**风险**:记忆方案要防止术语表把错误 OCR/错误翻译"固化"传播;建议只对出现
频次高、且 LLM 判定为专有名词的条目入表。

### 1.3 翻译时传入块坐标上下文

**现状**:`translator.py` 的 SYSTEM_PROMPT 只收到纯文本数组;`ocr.py` 的
`merge_lines()` 按 `(y, x)` 排序拼接文本。**竖排气泡(日漫)的块间阅读顺序
经常是错的**,LLM 只能靠猜,上下文连贯性受损。

**方向**:

- 把每个块的相对坐标/列序写进 prompt(例如 `[块3 | 右列,偏上] ...`),让 LLM
  按视觉顺序理解;
- 或先做更聪明的块内排序(竖排块内按 x 从左到右、再按 y 排序),减少交给
  LLM 的歧义;
- 注意坐标信息要脱敏成"相对位置描述",不要整张图的原始像素坐标(没意义且
  占 token)。

**风险**:低。prompt 模板改动需要回归验证(`test_smoke.py` 可扩展断言)。

### 1.4 `/config` 返回 `has_key`,修正状态页假信息

**现状**:`server/main.py` 状态页 HTML 中有行自我暴露的注释:
`const hasKey=p.id?true:true; // /config 不回 key,有 profile 即视为配过`。
也就是说状态页永远把"有供应商"显示成"已配置 API Key",而 README 常见自查
却引导用户"检查有没有已配置 API Key"——自查页给的是假信息。

**方向**:`/config` 对每个 profile 增加布尔字段 `has_key`(只回布尔,不回
key),状态页、前端向导据此显示真实状态;`list_profiles()` 相应增加该字段。

**风险**:极低。注意 `/config` 的无密钥约束保持不变(PRD 9.2)。

### 1.5 韩语 OCR 稳定性 ✅ 已落地（2026-08，paddleocr 3.7 / ocrt-vl）

**现状**:README 已知限制与 PRD 第 15 节都承认:PaddleOCR 3.x 韩语仍间歇性
失败,同一短语换字号可能成功/失败,日/英可靠。

**已实施**(基准:`server/tests/bench_ocr.py`,合成韩语页 5 行混排字号 56~18px):

- **低置信度行裁剪重试**(`ocr.py` `_retry_low_conf`):诊断发现韩语失败主因是
  整页识别时检测框质量差 → 正确文本被识成低置信乱码(conf<0.5),在进门门槛处
  就被丢弃;而同一行单独裁剪识别近乎完美(40~18px 全对,conf 0.94+)。
  修复:重试模式下进门门槛放宽到 0.3,弱行按原分辨率裁剪重试,救得回的留下,
  救不回的再按 0.5 收口。外扩边距实测 0.3 最优(0.15→recall 0.33,
  0.3/0.5→0.65,0.8→归零)。
- **默认只对韩语开**(`_retry_enabled`):recall 0.11 → 0.65,日/英 1.00 不受影响,
  耗时 +8%。`OCR_RETRY_LOW_CONF=1` 全语言开、`=0` 全关。
- 块输出新增 `conf`(组内行均值)供排查。

**剩余缺口**(不打算用重试解决,属检测/识别模型能力):
- 大字号(~56px+)韩语单行重试也失败——「同短语换字号」的模型级问题;
- 检测完全漏框的行重试无从下手(22px 行在合成页上漏检)。

**已否掉的手段**(实测/原理不成立):
- ~~japan/ch 模型交叉验证~~:识别模型训练集没有谚文,japan 模型对谚文输出
  必然是乱码,「取一致结果」在原理上不可能一致;
- ~~`PP-OCRv5_mobile_det`(韩语)~~:合成页识别直接归零(0 块)。

## 2. 性能方向

> 先读 PRD 第 15A 节:多项性能手段已实测否定(堆实例仅 1.1x、跳过空白切片
> 无收益等)。本节只列**尚未实测**或有新依据的方向。

### 2.1 轻量检测/识别模型 ✅ 已落地（2026-08）

**现状**:`server/ocr.py` 的 `_new_ocr()` 未传检测模型配置,走 PaddleOCR 默认
(较重)模型。

**已实施**:`OCR_DET_MODEL` / `OCR_REC_MODEL` 环境变量(`.env`,重启生效),
仅 paddleocr 3.x 传入 `text_detection_model_name` / `text_recognition_model_name`。

**实测**(合成页基准,ocrt-vl,CPU):
- `PP-OCRv6_small_det`(日/英):精度 1.00 不变,单页 5.36s → 2.92s,**接近提速一倍**;
- `PP-OCRv6_tiny_det`(日):精度 1.00,2.56s;
- `PP-OCRv6_small_rec`(日):精度 1.00,4.04s(收益有限);
- `PP-OCRv5_mobile_det`(韩语):识别归零,**有害**。

**未设为默认**:合成页是干净白底黑字,真实漫画背景复杂,小模型的漏检风险
未经真实页面验证。CPU 用户想提速可自行设置 `OCR_DET_MODEL=PP-OCRv6_small_det`,
先跑基准对比。换默认需补一轮真实页面数据。

### 2.2 GPU 路径完善 ✅ 已落地（2026-08）

**现状**:`gui.py` 已能选 GPU 环境启动,但后端对运行设备无感知:没有设备检测、
没有 CPU 回退提示,`/ocr-status` 也不展示设备。

**已实施**:
- `ocr.py` `device_info()`:惰性探测 + 缓存(`paddle.is_compiled_with_cuda()` +
  `cuda.device_count()`),`/ocr-status` 返回 `"device":"gpu"|"cpu"|"unknown"`;
- 首次建 OCR 实例打一行明显日志,CPU 时附提示「如需加速请用 GPU 环境启动」,
  取代静默回退;
- 状态页新增「运行设备」行(gpu 绿 / cpu 黄),常见自查加「速度莫名慢 → 看设备」;
- README GPU 章节补验证命令与常见坑(装了 CPU 版 paddlepaddle、cudnn 版本不配)。

### 2.3 切片并行(先测量再决定)

**现状**:`run_ocr()` 对超长条漫串行 `for` 循环切片识别(760x15000 约 19 片)。

**方向**:线程池并行切片。**但预期收益有限**——15A 的结论是 CPU 已接近饱和,
并行受制于核数;必须像 15A 那样先做真实条漫图的 A/B 测量,无收益即放弃。

### 2.4 LLM 分批并行

**现状**:`translator.py` 按 `CHUNK=25` 串行分批,一页 100 块 = 4 次串行往返,
每批还有重试退避,大页延迟叠加明显。

**方向**:并行发批后按序合并。代价是批次间上下文连贯性略降(LLM 看不到同一
页的其他批次),需要在"延迟 vs 连贯性"上权衡,或折中为"两批并行"。

## 3. 产品与分发方向

### 3.1 打包分发,降低门槛

**现状**:已有 `start-server.bat` / `start-gui.bat`,但用户仍需装 Python、
跑 pip 安装、首次使用时下载几百 MB OCR 模型——这是当前最大的使用门槛。

**方向**:

- PyInstaller 把后端打成 Windows exe(含 GUI 控制台),免装 Python;
- 模型预下载脚本/安装包内预置常用模型;
- Greasy Fork 发布流程文档化(自动更新链路已在用,发布动作本身可规范)。

**风险**:中。打包链路需要维护(PaddleOCR 动态库在 exe 里较折腾),建议先做
实验验证可行性再承诺。

### 3.2 站点规则(per-site 过滤阈值)

**现状**:`userscript` 的候选过滤是全局启发式(`MIN_SIZE=250`、`MAX_RATIO=2.5`
、`inChrome()` 排除页头页脚、`big()` 三级判断)。PRD 第 16 节已把 per-site
rules 列入 future。

**方向**:为已知主流合法漫画站维护最小规则集(阈值覆盖/额外选择器),解决
特定站点漏图(阈值太严)或误抓(UI chrome 被当漫画)。规则表应小且可审查。

### 3.3 inpainting 模式与元数据导出

**现状**:PRD 第 16 节已立项。注意 PRD 第 15 节明确"不擦除原文是核心价值",
inpainting 只能作为**独立的高级工作流**,不能替代默认覆盖层。

### 3.4 自定义翻译 prompt

**现状**:SYSTEM_PROMPT 硬编码在 `translator.py`。

**方向**:高级用户可自定义语气/风格/术语表(prompt 模板存 `.env` 或服务端
配置,不进浏览器存储)。风险低,但要注意 prompt 注入面只面向本地用户自己。

### 3.5 覆盖层样式扩展

**现状**:覆盖层固定"白底黑字"风格,失败态淡黄底。

**方向**:无背景只改字色(还原度)、原文/译文对照显示、自定义配色。都是纯
前端渲染层改动,不动 OCR/翻译链路。

## 4. 工程卫生

### 4.1 魔法数字配置化

**现状**:`POOL_SIZE=3`、`CPU_THREADS=5`(`ocr.py`)、`CONCURRENCY=4`、
`PRELOAD='1200px'`、`MIN_SIZE`/`MAX_RATIO`(userscript)、`RETRIES=3`、
`CHUNK=25`(`translator.py`)等散落在代码里,不同机器调优要改代码。

**方向**:搬进 `server/.env`(后端)与用户脚本顶部配置块(前端),保持默认值
不变。风险极低。

### 4.2 结构化错误码

**现状**:后端 `detail` 是中文串,前端靠 `errServer`/`errTimeout`/`NOTIMAGE`
/`TAINTED` 等中英混合字符串区分错误;PRD 已知限制"后端错误串只有中文,
UI 本地化不覆盖它们"。

**方向**:API 错误响应加机器可读 `code` 字段,前端按码映射到五语言文案。
错误串仍保留给人看。

### 4.3 限流退避优化

**现状**:`translator.py` 对可重试错误固定退避 `1.5s * (i+1)`,不读
`Retry-After` 头。

**方向**:429 时优先使用 `Retry-After`,普通退避加随机抖动,减少多并发请求
同步重试导致的再次限流。

### 4.4 Python 版本兼容性验证

**现状**:文档声明 Python 3.9–3.12,但 `server/__pycache__` 里存在
`cpython-313` 的 pyc,说明本机用 3.13 跑过。PaddleOCR 对 3.13 的支持情况
未经验证写进文档。

**方向**:在 3.13 下跑通 OCR 冒烟 + 一次真实翻译;通过则更新 README 支持
范围,不通过则锁定版本提示。

## 5. 不要重复尝试的方向(PRD 第 15A 节已实测否定)

以下方向已实现并测量过、不划算,除非有新证据,不应再作为 TODO 立项:

| 方向 | 实测结果 |
|---|---|
| 漫画专用文本检测器(comic-text-detector ONNX) | 两轮均更差(109 vs 142 字符等),多出的命中是噪声 |
| 放宽 PaddleOCR 检测阈值 | 最多 +3.5%,且是碎片噪声 |
| 增大文本框膨胀 `unclip=2.5` | 142 → 123 字符,变差 |
| 跳过空白切片 | 19 片中 0 片空白,无收益 |
| 更多 OCR 实例(CPU) | 最优组合仅 ~1.1x,CPU 已饱和 |
| overlay 挂进图片容器"原生跟随" | 与标准方案漂移相同(300px) |

## 7. 建议实施顺序

1. **第一轮(零风险快赢)**:1.4 has_key 修正 → 1.1 API 层测试 → 4.1 配置化。
2. **第二轮(核心体验)**:1.2 术语一致性 → 1.3 坐标上下文,配套测试。
